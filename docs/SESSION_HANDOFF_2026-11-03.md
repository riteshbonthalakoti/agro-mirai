## What changed this session (reverse chronological, roughly)

1. **Firebase/FCM set up from scratch.** The previous native `android/`
   directory (always gitignored, regenerated by `expo prebuild`) got wiped
   by a `--clean` prebuild before realizing `mobile/google-services.json`
   wasn't actually present anywhere in this checkout or in git (correctly
   gitignored as a credential, but the only local copy was living inside
   the old generated `android/app/`, now gone). No existing Firebase
   project was found for this app under either of the project's two
   Google accounts. **Created a brand new one** via the Firebase CLI:
   project ID `agro-mirai-push`, Android app registered under package
   `com.ritesh1918.mobile`, `google-services.json` downloaded to
   `mobile/google-services.json` (gitignored). A service-account key for
   FCM was also generated (`gcloud iam service-accounts keys create`) and
   sits at `mobile/firebase-adminsdk-key.json` (gitignored).
   - **Still open:** that service-account key needs uploading to EAS so
     Expo's push-notification relay can actually send through the new
     Firebase project. `eas credentials` is the only way to do this and
     it's a **fully interactive menu CLI with no non-interactive flag
     anywhere** (confirmed via `--help` at every level, tested
     `--non-interactive` directly — produces no error but also doesn't
     work). Multiple automation attempts this session (`winpty` + named
     pipe, a Python subprocess-pipe controller) ran into real tooling
     friction, not a fundamental wall — worth trying again with a fresh
     approach, or just finishing it by hand: `eas credentials -p android`
     → select `production` profile → Push Notifications → Google Service
     Account Key (FCM V1) → point it at `firebase-adminsdk-key.json`.
     Until this is done, push notifications won't actually deliver (the
     app will still request tokens fine, they just won't route anywhere).

2. **Three mobile bugs fixed**, from a real farmer-facing screenshot:
   - Chatbot gave a nonsensical "no data" refusal when asked to switch
     language mid-chat (e.g. "speak in Telugu") instead of explaining that
     language follows the app setting. Fixed in
     `src/agro_mirai/api/text_chat_client.py` — scoped the
     grounded-data-only rule to actual farming questions, added an
     explicit rule for language-switch requests.
   - Duplicate push notifications: two independent code paths in
     `mobile/src/backgroundAlerts.ts` (a per-advisory "fresh severe alert"
     and a once-daily digest) could both fire for the same top advisory in
     one run. Fixed to skip the digest when today's top advisory was
     already covered by the specific alert.
   - Chat input bar hidden behind the keyboard on Android:
     `KeyboardAvoidingView` is unreliable inside a transform-animated
     bottom-sheet `Modal` (confirmed as a known, field-documented pattern,
     not unique to this app — see commit message / research notes).
     Replaced with a manual `Keyboard.addListener` height tracker in
     `mobile/src/components/ChatAssistant.tsx`.

## Infrastructure quirks worth knowing before touching deploys again

- **Vercel (`agromirai` project) was never connected to GitHub auto-deploy**
  for most of this session — every "deployment" was a manual `vercel --prod`
  CLI push (`source: "cli"` in the deployment metadata). `vercel git connect`
  was run partway through this session to fix that going forward, but if a
  `git push` to `main` doesn't seem to deploy the landing page, don't assume
  it's broken — verify via `vercel ls` / the deployment list, and fall back
  to `cd web/landing && npx vercel --prod --yes` if needed.
- **Two separate Render accounts exist** for this project:
  `bonthalakotiritesh@gmail.com` (has a parallel, mostly-empty
  `agro-mirai`/`agro-mirai-cnn` deployment with none of the LLM API keys
  configured) and `riteshbonthalakoti@gmail.com` (the **real** production
  deployment — `agro-mirai`, `agro-mirai-cnn`, `agro-mirai-voice`,
  `agro-mirai-voice-heavy`, with all real API keys). Always confirm which
  account/workspace is active (`render workspace current`) before trusting
  `render` CLI output.
- **`agro-mirai-voice-heavy` isn't declared in `render.yaml`** — it was
  created outside the Blueprint, has no `buildFilter`, and rebuilds on
  every push regardless of relevance. A deploy failure for it earlier this
  session (`SigningConfig`-unrelated — that was mobile; this was a genuine
  one-off OOM kill during model loading) turned out to be a transient,
  self-resolved incident, not a recurring problem — but it's still
  unmanaged infra worth folding into `render.yaml` with a proper
  `buildFilter` at some point.
- **The project's real quota-monitoring system already exists and works**:
  `src/agro_mirai/api/quota_monitor.py` + `tools/quota_alert_sweep.py`,
  run every 2 hours via `.github/workflows/quota_alert_sweep.yml`, emails
  the admin once any OpenRouter/Groq key pool drops below 20% of its daily
  free-tier quota. Use `quota_monitor.check_all_pools()` directly (not the
  full sweep script, which sends real emails) to check current usage
  without side effects.
- **Render's API key for direct REST calls** (bypassing the CLI, which has
  no `env` subcommand in the installed version) lives in
  `~/.render/cli.yaml` under `api.key` — useful for pulling real env var
  values via `https://api.render.com/v1/services/<id>/env-vars` when the
  CLI itself can't.

## If continuing the push-credential upload

Don't re-derive the "no non-interactive path exists" finding — it's
confirmed, not assumed. The real options from here:
1. Just do it by hand in a terminal (fastest, ~2 minutes of clicking).
2. Try the Expo web dashboard
   (`https://expo.dev/accounts/ritesh.bonthalakoti/projects/agro-mirai/credentials`)
   instead of the CLI — needs the user to log in first (don't attempt to
   log in on their behalf).
3. If automation is worth another attempt: a Python `subprocess.Popen`
   with real `stdin=PIPE`/`stdout=PIPE` (not a named FIFO, which has
   blocking-pair-up semantics that caused a deadlock earlier) driven by a
   small persistent controller process, fed commands by appending to a
   plain file across separate tool calls, is the most promising approach
   tried so far — just didn't get finished before this handoff was written.
